# Асинхронный сервис процессинга платежей

Тестовый сервис на Python 3.12, FastAPI / Pydantic v2, SQLAlchemy 2 async,
PostgreSQL, RabbitMQ / FastStream и Alembic. Платёжный шлюз эмулируется:
обработка занимает 2–5 секунд, примерно 90% ID платежей дают успех;
результат стабилен для повторных вызовов с тем же ID.
Реальные списания денег не выполняются.

## Быстрый запуск

Нужны Docker Engine и Docker Compose v2.

```bash
cp .env.example .env
# Замените API_KEY в .env на случайный ключ длиной не менее 16 символов:
python -c 'import secrets; print(secrets.token_urlsafe(32))'
```

Укажите в `.env` точный HTTPS-хост вашего webhook-приёмника:

```dotenv
WEBHOOK_ALLOWED_HOSTS=["hooks.example.com"]
WEBHOOK_ALLOW_HTTP=false
```

`hooks.example.com` — пример, а не готовый сервер. Нужен ваш работающий
приёмник, возвращающий HTTP 2xx. По умолчанию список пуст: ни один адрес
webhook не разрешён. Для локального тестового HTTP-приёмника можно явно
добавить его хост и включить `WEBHOOK_ALLOW_HTTP=true`; это не настройка
для публичного развёртывания. `localhost` внутри consumer — сам контейнер,
а не компьютер разработчика.

```bash
docker compose up --build -d
docker compose ps
docker compose logs -f api consumer
```

Compose поднимает ровно четыре сервиса: `postgres`, `rabbitmq`, `api`,
`consumer`. API ждёт готовности БД/брокера, применяет миграции, затем
запускает HTTP-сервер. Consumer стартует после успешной проверки API,
поэтому миграции уже выполнены. Только API доступен с хоста, и только
на `127.0.0.1:8000`. БД и брокер сохраняют данные в именованных volumes.

```bash
docker compose down
# Полный сброс тестовых данных (необратимо):
# docker compose down -v
```

## API

Все эндпоинты, включая `/health`, требуют `X-API-Key`. Укажите тот же ключ,
который записан в `.env`:

```bash
export API_KEY='ваш-ключ-из-env'
curl --fail-with-body http://localhost:8000/health \
  -H "X-API-Key: $API_KEY"
```

Создание платежа:

```bash
curl --fail-with-body -i http://localhost:8000/api/v1/payments \
  -H "X-API-Key: $API_KEY" \
  -H 'Idempotency-Key: order-1001' \
  -H 'Content-Type: application/json' \
  -d '{
    "amount": "1250.50",
    "currency": "RUB",
    "description": "Заказ 1001",
    "metadata": {"order_id": "1001"},
    "webhook_url": "https://hooks.example.com/payments"
  }'
```

Ответ — `202 Accepted`, `payment_id`, `status`, `created_at`.
Сумма передаётся строкой, чтобы не терять точность decimal.
Валюты: `RUB`, `USD`, `EUR`.

```bash
export PAYMENT_ID='uuid-из-ответа'
curl --fail-with-body "http://localhost:8000/api/v1/payments/$PAYMENT_ID" \
  -H "X-API-Key: $API_KEY"
```

Повторите POST с тем же ключом и тем же телом: новый платёж не создаётся.
Использование того же ключа с другим содержимым возвращает конфликт.
Платёж принимает статусы `pending`, `succeeded`, `failed`.

## Как устроены доставка и повторы

1. API сохраняет платёж и запись `outbox` в одной транзакции PostgreSQL.
   Нет окна, в котором платёж уже принят, но событие потеряно из-за
   недоступности RabbitMQ. Уникальное ограничение на idempotency key
   защищает также от конкурентных POST.
2. Фоновый publisher в процессе consumer резервирует batch outbox короткой
   транзакцией с `FOR UPDATE SKIP LOCKED` и lease. Публикация persistent-
   событий с publisher confirms выполняется вне транзакции БД; подтверждение
   фиксируется с проверкой ownership. Истёкший lease позволяет повторить
   публикацию после сбоя процесса. Дубли по-прежнему возможны.
3. Обработчик получает lease платежа в короткой транзакции, вызывает шлюз
   вне транзакции/пула БД, фиксирует результат с проверкой lease-token,
   затем аналогично отправляет webhook. DB fencing не даёт устаревшему
   владельцу перезаписать результат, но не отменяет уже начатый сетевой
   запрос. Истечение lease не гарантирует отсутствие повторного вызова
   провайдера: нужна его собственная идемпотентность.
4. Повторная доставка терминального платежа не запускает оплату заново;
   незавершённая доставка webhook может повториться. Исключения допускают
   всего три бизнес-попытки с задержками 1 и 2 секунды. Попытки и
   запланированные retry/recovery-события сохраняются в БД через outbox.
   После падения worker обработка восстанавливается по истечении lease
   (`PROCESSING_LEASE_SECONDS=45` по умолчанию), а не сразу.
5. После третьей ошибки шлюза платёж становится `failed`, выполняется
   попытка уведомить клиента об этом, затем событие отправляется в DLQ
   через outbox. После третьей ошибки доставки webhook также используется
   DLQ; уже успешный платёж не отменяется. Ошибки инфраструктуры БД
   возвращают сообщение в очередь и не расходуют бизнес-попытки.

Эмулятор ждёт 2–5 секунд. Результат стабильно вычисляется по хешу ID
платежа: примерно 90% платежей `succeeded`, 10% `failed`. Это не новая
лотерея при retry. Штатный `failed` — терминальный результат, не
транспортное исключение, и не вызывает повторную оплату.

### Формат webhook

POST с JSON, заголовками `X-Event-ID` и `Idempotency-Key`, содержащими
один стабильный идентификатор `payment.<payment_id>.completed`:

```json
{
  "event_id": "payment.<payment_id>.completed",
  "payment_id": "<payment_id>",
  "status": "succeeded",
  "amount": "1250.50",
  "currency": "RUB",
  "metadata": {"order_id": "1001"},
  "processed_at": "2026-10-24T12:00:00+00:00"
}
```

Ответ 2xx подтверждает доставку; HTTP-ошибки и сетевые исключения
вызывают повтор. Редиректы не выполняются и считаются ошибкой.

### Важные ограничения

- Гарантия — **at least once**, не exactly once. Если брокер подтвердил
  публикацию, но процесс упал до фиксации outbox, событие будет опубликовано
  повторно. Consumer должен выдерживать такие дубли.
- Приёмник webhook должен дедуплицировать уведомления по стабильному ключу
  события: сетевой timeout не доказывает, что получатель не обработал запрос.
  Нельзя атомарно зафиксировать PostgreSQL и HTTP-вызов чужого сервиса.
- Ошибка webhook не отменяет уже успешный платёж. DLQ означает проблему
  обработки/доставки, а не обязательно неуспешное списание.
- Детерминированный эмулятор шлюза — демонстрация. В реальной интеграции потребуется
  idempotency key на стороне провайдера и сверка неопределённых результатов.
- По умолчанию consumer последователен. Параллельный режим использует
  lease/token fencing; устойчивость при падениях и истечении lease нужно
  проверять с реальным провайдером и его idempotency key.

## Безопасность

API key берётся из окружения; пример из `.env.example` предназначен только
для локального запуска. `.env` не следует коммитить. Webhook требует HTTPS
(кроме явно включённого локального режима), точного allowlist хостов и не
следует редиректам. Это снижает SSRF-риск, но не заменяет production-защиту:
нужны контроль исходящего трафика, DNS/IP-проверки против rebinding,
блокировка private/loopback/link-local/metadata IP и доверенный список
получателей. Не добавляйте произвольные пользовательские хосты в allowlist.

Для production также нужны TLS на входе, безопасные пароли БД/брокера,
хранилище секретов, подпись webhook, rate limiting, наблюдаемость и
политика очистки outbox / хранения idempotency keys. Тестовые credentials
`payments:payments` нельзя использовать публично.

## Разработка и проверки

Установите Python 3.12 и uv; зависимости фиксируются в `uv.lock`.

```bash
uv sync --frozen
uv run pytest -q
uv run ruff check .
```

Юнит-тесты используют отдельную SQLite БД и не требуют Docker. Проверка
конкурентных запросов с настоящим PostgreSQL выполняется отдельно:

```bash
TEST_DATABASE_URL='postgresql+asyncpg://payments:payments@localhost:5432/payments' \
  uv run python -m pytest tests/test_api.py -m integration -q
```

Нужен доступный PostgreSQL и пользователь с правами CREATE/DROP SCHEMA:
тест создаёт уникальную временную схему, не удаляя существующие таблицы.
Compose по умолчанию не публикует порт PostgreSQL; для запуска теста с хоста
используйте отдельную тестовую БД или временный Compose override с
`ports: ["127.0.0.1:5432:5432"]` у сервиса `postgres`.
Проверка настоящего RabbitMQ (publisher confirms, persistent-сообщения,
mandatory/unroutable и DLQ) тоже включается явно:

```bash
TEST_RABBITMQ_URL='amqp://payments:payments@localhost:5672/' \
  uv run python -m pytest tests/test_broker.py -m integration -q
```

Нужен доступный тестовый брокер; для Compose временно опубликуйте
`127.0.0.1:5672:5672` у `rabbitmq`. Тест создаёт и удаляет только свои
очереди с уникальным префиксом, не трогая очереди приложения. Если переменные
`TEST_DATABASE_URL` / `TEST_RABBITMQ_URL` не заданы, соответствующие
интеграционные тесты пропускаются. Остальные тесты используют SQLite,
моки и тестовый транспорт FastStream, а не настоящую инфраструктуру.

Миграции в работающем окружении:

```bash
docker compose exec api alembic current
docker compose exec api alembic upgrade head
```

## Структура

Сначала выделяется приложение, внутри него — слои. Общие настройки и
инфраструктура вынесены отдельно; новые предметные приложения можно
добавлять рядом с `payments`.

```text
app/
├── main.py                 # сборка FastAPI и общие HTTP-эндпоинты
├── core/                   # настройки и аутентификация
├── payments/
│   ├── api/                # HTTP-маршруты платежей
│   ├── schemas/            # входные/выходные схемы и события
│   ├── models/             # модель Payment
│   ├── repositories/       # создание платежа с transactional outbox
│   ├── services/           # обработка платежа и политика повторов
│   └── integrations/       # эмулятор шлюза и webhook-клиент
└── infrastructure/
    ├── database/           # engine, сессии, Base и модель Outbox
    └── messaging/          # RabbitMQ consumer и outbox publisher
```

- `migrations/` — Alembic и исходная схема `payments` / `outbox`.
- `tests/` — проверки API, идемпотентности, обработки и брокера.
- `compose.yaml` — PostgreSQL, RabbitMQ, API и один consumer.

Точки входа: `uvicorn app.main:app` и
`python -m app.infrastructure.messaging.worker`.

## Проверка сценариев вручную

1. Отправьте POST и затем GET: сначала `pending`, затем терминальный статус.
2. Повторите тот же POST: тот же ID и отсутствие повторного создания.
3. Для проверки retry используйте ваш webhook-приёмник, отвечающий HTTP 500:
   после трёх ошибок сообщение должно попасть в `payments.dlq`.
4. Остановите брокер после запуска сервисов, создайте платёж, затем запустите
   брокер снова: outbox должен доставить сохранённое событие после восстановления.
5. Перезапустите consumer между попытками: счётчик и отложенный повтор
   должны сохраниться в PostgreSQL.

Логи: `docker compose logs -f consumer`. Проверить состояние очередей:

```bash
docker compose exec rabbitmq rabbitmqctl list_queues name messages_ready messages_unacknowledged
```

## Масштабирование и цель 10 000 RPS

**10 000 RPS — целевой профиль нагрузки, а не подтверждённая
производительность этой реализации.** Приём запроса с `202` и завершение
платежа — разные метрики. Приведённые ниже параметры и стенд позволяют
проверить пределы системы; они не заменяют измерения на конкретном железе.

### Ограничение эмулятора и ёмкость

При последовательной обработке шлюз занимает в среднем 3,5 секунды:
один execution slot завершает примерно `1 / 3.5 = 0.29` платежа/секунду
ещё до учёта webhook, БД и повторов. Для 10 000 завершений/секунду
арифметическая нижняя оценка — **35 000 одновременно выполняемых
платежей**, а не 35 000 HTTP RPS. Это не рекомендация запускать столько
coroutine на одном сервере. Нужны лимиты провайдера, контроль соединений,
производительность webhook-приёмников, запас на tail latency и retries.

Профиль `load/k6.js` по умолчанию смешанный: 70% новых POST, 20%
идемпотентных повторов, 10% GET. При 10 000 RPS это 7 000 новых
платежей/секунду, то есть около 24 500 in-flight операций только шлюза
для устойчивого завершения такого потока. При меньшей скорости consumer
очередь растёт; краткий быстрый API-тест не доказывает устойчивую ёмкость.

### Параметры и развёртывание

- `WORKER_CONCURRENCY=1` сохраняет требование исходного задания: один
  обработчик. Параллелизм и число реплик consumer увеличиваются отдельно
  и только по результатам тестов. Lease/token fencing защищает изменения в БД от устаревшего владельца,
  но не исключает одновременные сетевые вызовы при истечении lease. Внешний
  провайдер обязан поддерживать идемпотентность и сверку результатов.
- `DATABASE_POOL_SIZE=10`, `DATABASE_MAX_OVERFLOW=0` задают ограниченный
  пул каждого процесса. Сетевые ожидания шлюза/webhook не должны занимать
  транзакцию БД. Общий бюджет соединений: сумма пулов всех API и worker
  процессов плюс миграции/операционные подключения. Умножать реплики без
  этого расчёта нельзя; при необходимости используйте совместимый pooler.
- `OUTBOX_BATCH_SIZE=100`, `OUTBOX_PUBLISH_CONCURRENCY=10` ограничивают
  размер выборки и параллелизм публикации. Измеряйте publisher-confirm
  latency, время SQL-транзакций и возраст старейшей неопубликованной записи.
- `API_MAX_PENDING_PAYMENTS=100000` — **мягкий глобальный порог** backlog,
  а не атомарная строгая квота. Каждая API-реплика кеширует снимок общего
  backlog из БД раз в `BACKLOG_REFRESH_SECONDS=1`. Новые POST получают
  `429`, если снимок достиг лимита либо устарел более чем на три интервала.
  Уже существующий idempotent replay не блокируется этим gate. Между
  обновлениями возможен overshoot порядка суммарной скорости новых
  запросов × окно обновления плюс in-flight запросы всех реплик; это
  оценка, а не строгая верхняя гарантия. Настройки реплик должны совпадать.
- `API_MAX_INFLIGHT=256` отдельно ограничивает одновременные HTTP-запросы
  каждого API-процесса (`429` при перегрузке); `API_MAX_BODY_BYTES=65536`
  ограничивает тело 64 KiB (`413`). Этот per-process limiter может отклонить
  и replay/GET: освобождение от backlog gate не означает обход всех лимитов.
- Защищённый тем же `X-API-Key` `GET /internal/backlog` возвращает
  `pending_payments`, `pending_outbox`, `limit`, `accepting_new_payments`,
  `snapshot_age_seconds`. Это кешированный снимок, не синхронный пересчёт
  на каждый запрос; мониторинг должен учитывать его возраст.
- Production API запускается несколькими stateless-репликами за
  балансировщиком с keep-alive, TLS, health/readiness checks и лимитами.
  Миграции выполняются **одной отдельной release job**, а не каждой репликой.
  Контейнер API запускает только `uvicorn app.main:app ...`.
- Исходный Compose — локальный стенд. Его `api` публикует фиксированный
  host-порт 8000 и выполняет миграции при старте, поэтому простой
  `--scale api=N` не является корректным production-развёртыванием.
  В production-манифесте уберите host-port у реплик и выделите отдельный LB;
  увеличивайте API и worker независимо. Отдельного «10k-ready» манифеста,
  который обещает ёмкость без проверки, здесь намеренно нет.

Масштабирование не отменяет ограничений одной PostgreSQL primary и
RabbitMQ. Нужны измерения WAL/IOPS, конфликтов уникального индекса,
блокировок, размера outbox/индексов, queue depth, возраста сообщений,
активных lease, completion rate и webhook latency. Установите сроки
хранения опубликованного outbox и idempotency keys; удаление последних
меняет гарантию защиты от повторных клиентских запросов.

### Безопасный локальный нагрузочный стенд

Используйте отдельный Compose project и новые тестовые volumes. Следующие
команды создают только локальный стенд; внешние webhook не вызываются:

```bash
cp .env.example .env  # если файл ещё не создан; не перезаписывайте рабочие секреты
# Установите свой API_KEY длиной >= 16 символов.
docker compose -p payments-load -f compose.yaml -f compose.load.yaml up --build -d
# В другом терминале; по умолчанию 100 RPS, 30 секунд:
docker compose -p payments-load -f compose.yaml -f compose.load.yaml run --rm k6 run /load/k6.js
```

`compose.load.yaml` добавляет только локальный HTTP webhook sink и k6;
устанавливает точный allowlist `["webhook"]` и разрешает HTTP лишь для
стенда. Receiver не имеет публичного порта. Это не production-конфигурация
и не высокопроизводительный benchmark webhook-приёмника. Базовые четыре
сервиса и последовательный consumer по умолчанию сохраняются. Порт 8000
должен быть свободен: не запускайте стенд одновременно с основным Compose.

По умолчанию сценарий ограничен 100 RPS × 30 секунд, то есть примерно
2 100 новых платежей плюс один seed. После окончания подачи нагрузки
consumer продолжает обрабатывать накопленное. Проверяйте остаток очереди;
не считайте тест завершения платежей законченным, пока очередь не опустела.
Для удаления только изолированных тестовых данных после проверки:

```bash
docker compose -p payments-load -f compose.yaml -f compose.load.yaml down -v
```

Осторожно: `down -v` необратимо удаляет volumes именно указанного project.

### Профиль 10 000 RPS и критерии приёмки

Повышайте нагрузку ступенчато (100 → 500 → 1 000 → 5 000 → 10 000),
сначала проверив ограничения стенда. Следующий пример запускает целевой
профиль только по явному флагу, в изолированном окружении:

```bash
docker compose -p payments-load -f compose.yaml -f compose.load.yaml run --rm \
  -e RATE=10000 -e DURATION=30s -e CONFIRM_HIGH_LOAD=true \
  k6 run /load/k6.js
```

30 секунд — короткий диагностический прогон, не доказательство steady state.
70% новых POST при таком профиле создали бы около 210 000 платежей за
30 секунд, если бы они были приняты без остановки монитором: default admission limit и один consumer закономерно
ограничат этот поток. Не повышайте лимит, чтобы просто скрыть перегрузку;
сначала обеспечьте и измерьте скорость завершения.

Скрипт проверяет backlog до старта и примерно раз в 5 секунд отдельным
контрольным сценарием. Если `pending_payments` или `pending_outbox`
превышает `MAX_BACKLOG=5000`, вызывается `exec.test.abort`: подача нагрузки
останавливается. Недоступность мониторинга тоже останавливает тест.
Это защитная проверка с дискретным опросом, не строгий лимит: за 5 секунд
при высокой скорости очередь может заметно вырасти. После abort worker
продолжает обрабатывать уже принятые платежи. Поднимать `MAX_BACKLOG`
допустимо только осознанно в изолированном стенде с достаточным запасом.
Контрольные HTTP-запросы (примерно 0,2 RPS и один до старта) и setup seed
добавляются сверх заявленного профиля; они исключены из пользовательских
latency/error-метрик и помечены `traffic=control` для backlog-запросов.

Три нагрузочных сценария используют constant-arrival-rate;
одна итерация — один запрос.
`PREALLOCATED_VUS` и `MAX_VUS` можно переопределить (значения применяются
к каждому из трёх нагрузочных сценариев). Следите и за CPU/сетью генератора: отсутствие
свободных VU либо насыщение генератора не доказывает предел сервиса.
Для теста удалённого **своего изолированного** стенда необходимы явные
`ALLOW_REMOTE_TARGETS=true`, `ALLOWED_API_HOSTS` и
`ALLOWED_WEBHOOK_HOSTS` с точными именами хостов, а также `BASE_URL` и
`WEBHOOK_URL`. API имеет свой независимый webhook allowlist. По умолчанию
скрипт разрешает только localhost/loopback и имена локальных Compose-сервисов.
Редиректы не выполняются, ключи не логируются.

Автоматические пороги k6:

- `admitted_request_duration`: p95 < 200 мс, p99 < 500 мс только для
  ответов 202/200; быстрые 429 не улучшают эту метрику искусственно.
- `unexpected_errors`: < 1%; только 429 для **новых** POST считается
  контролируемым admission rejection, а не неожиданной ошибкой.
- `admission_rejected`: 0 по умолчанию. Для отдельного теста механизма
  защиты можно задать `MAX_ADMISSION_REJECTIONS`, но такой прогон **не
  является успешной проверкой заявленной ёмкости**.
- `dropped_iterations`: 0, то есть генератор действительно отправил
  запланированные запросы; `checks` > 99%, включая сохранение ID при replay.

Сохраните вывод k6, профиль/длительность, версии, конфигурацию CPU/RAM,
число реплик/пулы и данные инфраструктурного мониторинга. Пороги латентности применяются как к общей метрике, так и отдельно к
каждому из трёх сценариев, чтобы быстрые GET не скрывали медленные POST.
Затем отдельно измерьте end-to-end completion latency, drain time,
дубли/потери после рестартов и ровный backlog при длительной подаче.
Порог API сам по себе не является гарантией SLA завершения платежа.

Нагрузочный тест намеренно не запускается автоматически на публичной
инфраструктуре или платных ресурсах. Unit/integration CI и локальный
нагрузочный smoke проверяют разные свойства; прохождение тестов не
означает, что 10 000 RPS уже измерены. Формат сценариев и метрик:
[Grafana k6 scenarios](https://grafana.com/docs/k6/latest/using-k6/scenarios/),
[expected statuses](https://grafana.com/docs/k6/latest/javascript-api/k6-http/expected-statuses/).
